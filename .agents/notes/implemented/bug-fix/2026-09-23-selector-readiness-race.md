# Agent Note: selector 就绪竞态 —— 控制端口先接客、tunnel 后填充，404 打掉健康节点

Status: implemented

## Problem

生产闭环每轮都有若干次尝试报「Mihomo selector 切换失败（HTTP 404）」。它不产生不可恢复的失败（重试常常能过），但会**终态打掉健康节点**：run `35803348524` 里 69 次尝试撞上 16 次（≈23%），终态打掉 4 个节点（14/16/22/32），其中节点 32「德国」（`51.75.77.164`）三次尝试全部 404——它本来是健康节点。同时也污染报告口径：14/16/22 的终态文案从「网络不可达 / 拒绝连接」被换成 404。

难查的原因：文案里只有状态码，产物里的 `mihomo_error`（mihomo 日志尾巴）是空的（`log-level: warning` 时正常启动什么都不打）。

把范围收窄到源码：`MihomoProcess.select()` 先 `GET /proxies/BEST-IP`（非 2xx 就当作「没取到」继续），再 `PUT`；报错文案里的状态码取自 **PUT**。查 mihomo v1.19.30 的 `hub/route/proxies.go`：这条路由**只有一处**能回 404——chi 的中间件 `findProxyByName` 在 `tunnel.Proxies()` 里找不到这个名字（`updateProxy` 只回 400/204）。所以 404 的确切含义是「那一刻这个实例里没有这个组」。

**先说清楚上一轮的错误结论。** 改动前我写过「这是就绪竞态（`start()` 只等 `/version`、不等组注册）」，随后又用一次探针把它记为「实测证伪」：在 runner 上用生产代码路径（`MihomoProcess`，8 路并发 × 2 轮）跑 16 个实例，`start()` 返回后组端点全是 200、`select()` 全成功、一次 404 都没复现。**那次探针的判断方法本身是错的**，细节见下面「取证」。

## Decision

就绪判据补上「本次要用的 selector 组已注册」：`backend/app/mihomo.py::MihomoProcess._wait_until_ready()` 现在要求 `/version` 能应答 **且** `GET /proxies/BEST-IP` 是 2xx（新增 `_selector_registered()`），两者都在原来的 15 s 预算内。控制器就绪前的轮询间隔保持 0.2 s 不变，控制器就绪后改成 0.05 s。另外把「控制器起来了但组一直不注册」单列成新文案「等待 Mihomo selector 组注册超时」，与「等待 Mihomo 控制端口超时」分开。

选这个位置而不是在 `select()` 里加重试：`start()` 返回时就该意味着「这个实例可用了」。`node_runner` 在 `start()` 与 `select()` 之间不做别的动作，所以把条件放进就绪判据，所有调用方共享同一个定义。

## 取证：把「是不是就绪竞态」钉成事实

先把机制从源码上确认（v1.19.30）：

- `hub/hub.go::ApplyConfig` = `applyRoute(cfg)` → `executor.ApplyConfig(cfg, true)`；
- `applyRoute` → `route.ReCreateServer(...)`，函数体就是 `go start(cfg)`（起监听是**异步**的）；
- `executor.ApplyConfig` 里 `updateProxies(cfg.Proxies, cfg.Providers)` 在第 100 行，之后才是 rules/DNS/listeners；
- `tunnel.Proxies()` 返回的是被 `UpdateProxies` 整体替换的那个包级 map。

于是 404 在源码上只有一种可能：控制端口已经在应答，而 `updateProxies` 还没跑到。

再让失败现场自己说话。在探针分支 `probe/selector-404`（`2f59f0e`）给 `select()` 的失败路径加一次性取证（写进日志、不改语义），派一次真实扫描（run `35804379049`，60 次尝试、1 次 404）。那一次 404 的现场是：

- `listener_pid = 2534` == `child_pid = 2534`，`child_returncode = null` → 应答者**就是我们自己的子进程**，不可能是别的实例或别的服务；
- `written_secret_matches = true`，用假 secret 问 `/version` 得 **401**、用真 secret 得 200（`{"meta":true,"version":"v1.19.30"}`）→ 鉴权在、且它就是我们的进程；
- `written_groups` 就是 `[{name: BEST-IP, type: select, proxies: [<该节点>]}]` → 我们写下的配置里组是有的；
- 紧接着问 `GET /proxies` 得 200，9 个键里 `BEST-IP` 与该节点**都在**。

也就是说：组在几十毫秒后就有了，失败那一刻只是还没填。

最后量窗口宽度。同一分支（`f2f821f`）装上修复并顺手量「首次 `/version` 200」到「组端点首次 2xx」的时间差，再派一次真实扫描（run `35804645837`）：

- **60/60 次尝试都打印了这个滞后**——即每一次尝试在 `/version` 首次应答时组都还没注册；
- 其中 **25/60 的滞后 ≥ 50 ms**（50 ms 是控制器就绪后的轮询步长，所以这个下界说明组确实是在 `/version` 之后才注册的），其余 < 50 ms 的读数只是那次检查的请求耗时；min / 中位 / max = **1.0 / 26.6 / 58.8 ms**；
- 同轮 `select()` 的 404 取证 **0 次**；结果 30 成功 / 0 部分 / 10 失败，10 个失败正好是不可约集合（14/15/16/24..28「网络不可达」、22/23「拒绝连接」）。

**为什么上一轮探针 16/16 没复现**：那次把判据取成「`start()` 返回后组端点是否 200」，而老的就绪轮询是 **0.2 s** 一次，所以 `start()` 通常在 `/version` 首次成功后约 100 ms（最多 200 ms）才返回——早已越过 1~59 ms 的窗口（中位 27 ms）。那个方法**必然**得出「没复现」，它不是反证，只是探针没在窗口内采样（另外那次没有采集器负载，窗口本身也更窄）。

本机（16 核、空闲、8 路并发）同一时刻的窗口只有 0.2~0.7 ms；加 CPU 过载后 mihomo 启动被拉到秒级，但那次轮询自身退化成每次 2 s 的连接超时，分辨率不足以量窗口，只能当参考。

## Alternatives considered

- **维持「真因未知」、不动生产代码。** 最强理由：证据不够时改生产代码是把噪声当信号，而且上一轮已经栽过一次（把错因写错又撤回）。不用它的原因：这次把测量方法补对了（进程身份 + tunnel 内容 + 首次 `/version` 与组就绪的时间差），窗口在每一次尝试上都能量到；404 在源码里只有一个来源，与现场完全一致；继续不动等于把「就绪」留在一个与 `select()` 前置条件不匹配的定义上——后续任何调用方都会再踩一次。
- **只在 `select()` 里加短重试**（第一次 GET 拿不到就等 50 ms 再试）。最强理由：改动最小、只影响失败路径、能救回已经起来的实例。不用它的原因：那是把「就绪」的语义留在错的地方，真正的问题在 `start()` 的返回值上；而且重试会把「端口真的坏了」这类真失败拖成更慢的失败。
- **接受它不改**（它不产生不可恢复的失败，重试通常能过）。最强理由：代价只是多花一次尝试，成功率看不出差别。不用它的原因：run `35803348524` 一次就打掉健康节点 32，并把 3 个节点的终态文案换成 404——报告的口径被污染，正是这一轮闭环要修的东西。
- **把 404 当可重试静默丢弃。** 最强理由：最省事。不用它的原因：等于把证据擦掉，下一次真出问题（例如组名变了）就没有信号。
- **不给 DNS 引导路径单开逻辑。** 这个 404 与 DNS 引导候选无关：带引导（`dns_bootstrap_proxy != null`）和不带的节点都撞上过。

## Consequences

- **收益（实测）**：修好后 run `35804645837` 的 `select()` 404 为 **0 次**，10 个失败全部不可约，且没有一条失败文案是被 404 顶替的。同形状的改动前运行（run `35803348524`）是 16 次 404、4 条终态被顶替。
- **代价**：每次尝试多一次 `GET /proxies/BEST-IP`；实测窗口 1~59 ms，所以最坏情况多等几十毫秒（控制器就绪后的轮询步长是 0.05 s）。
- **代价（新文案）**：控制器起来了但组一直不注册时，`start()` 现在 15 s 后报「等待 Mihomo selector 组注册超时」。比旧行为（拖到 `select()` 里报 404）更精确，但这是一条新的失败文案。
- **仍未解释**：不同运行之间的 404 率差很多（run `35803348524` 是 16/69，run `35804379049` 是 1/60）。窗口宽度由调度决定，这种波动本身可预期，但本轮没有单独测量每台 runner 的负载，所以没有把「哪一轮为什么更宽」定量说清。
- **风险（未触发）**：就绪判据现在依赖「组端点 2xx」。如果哪天 mihomo 改了组端点的返回形状（例如组只在被选中后才出现在 `/proxies`），`start()` 会以「组注册超时」失败——那是显式失败，不会静默产生错的测量。
