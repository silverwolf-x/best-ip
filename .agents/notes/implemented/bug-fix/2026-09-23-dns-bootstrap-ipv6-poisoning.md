# Agent Note: DNS 引导候选池混入 IPv6 字面量节点，把能连的节点判成「域名无法解析」

Status: implemented

## Problem

2026-09-23 的生产闭环（run `35801218260`，40 个节点）留下 15 条失败记录，其中 13 条的原因写着「节点服务器域名无法解析」。[A2 笔记](../feature/2026-09-22-frontend-next-in-page-scan-trigger.md) 把这个信号结案成「订阅数据侧抖动，不是代码问题」，并写下「以后见 `scan_unavailable` 先查订阅内容与节点域名，别先怀疑信封或页面」。**这条结论是错的**——它把一把尺子（看见「域名无法解析」就归因订阅数据）当成了事实，而那个信号下面压着一个可复现的代码缺陷。三条证据：

（这条更正**不**推翻同一篇里那次连续三次 `scan_unavailable` 的地基：`neokocloud.host` 在三个公共解析器上确实是 NXDOMAIN，那是数据侧事实。但它同样取消了那次的**因果唯一性**——同一个「域名无法解析」信号现在有两个来源，按当时的证据分不开。）

1. **名字能解析。** 被记成「域名无法解析」的五个域名在三个公共 DoH 解析器（cloudflare / alidns / doh.pub）上都返回同一个 A 记录：`sg-fdc.aikunapp.com` → 67.159.52.89、`sg-fdc2.aikunapp.com` → 67.159.52.170、`cdncdn.aikunapp.com` → 104.21.93.88、`krgc.aikunapp.com` → 109.61.127.36。DNS 里名字是活的，节点却报解析失败。
2. **失败集合是可预测的。** 失败索引恰好是 2,3,4,14,15,16,22,23,24,25,26,27,28,38,39。把「引导候选按 `(node_index + attempt - 1) % len(候选)` 轮转」这条既有规则代进产物，能逐条预测每个 hostname 节点在第几次尝试成功，**18/18 与产物里的 `attempt_count` 逐条相同**（节点 5 → 3 次、6 → 2 次、7 → 1 次……），而「三次候选全是 IPv6」的那 8 个节点也全部失败。数据抖动不会抖出这种算术。
3. **候选池里 IPv6 正好占住事发位置。** 用生产同一份订阅、同一个解析器重放 `_dns_bootstrap_candidates`，候选池 12 个里 5 个是 IPv6 字面量，位置 2..6——所有失败索引的模都落在这 5 个位置上。

机制在 `backend/app/scan/node_runner.py`：hostname 节点需要一个「IP 字面量节点」当代跑 DNS 的出口，DoH 查询经它转发（`mihomo.py` 里拼成 `<resolver>#BEST-IP-DNS`）。`_dns_bootstrap_candidates` 的判据只有 `address.is_global`，于是 **IPv6 字面量节点也被收进池子**。但四个 DoH 解析器（223.5.5.5 / 1.12.12.12 / 1.1.1.1 / 8.8.8.8）全是 IPv4 字面量，引导出口必须能由本机 IPv4 栈到达；同一次运行里那 5 个 IPv6 字面量节点自己也全部连不上，于是它们代跑的 DNS 全灭，日志被 `_summarize_mihomo_error` 读成「节点服务器域名无法解析」。一个 A 记录正常、本来能连的节点就这样被判失败，并白烧三次尝试。

## Decision

`_dns_bootstrap_candidates` 只收 **全局 IPv4 字面量**：`address.version == 4 and address.is_global and name`。

判据不是「哪种更常见」，而是「引导出口必须能替本机把 DoH 查询送到那四个 IPv4 解析器」：一个 IPv6 字面量节点只有在运行环境自己有 IPv6 出口时才可能连上。生产运行环境（GitHub 托管的 ubuntu-24.04 runner）**没有可用的 IPv6 出口**——这不是猜的：runner 上 `ip -6 route` 只有 `fe80::/64`、`curl -6` 立刻失败、`socket.connect` 报 `Network is unreachable`，证据与官方说明见 [mihomo 允许 IPv6 笔记](2026-09-23-mihomo-allow-ipv6.md)。连不上时它不是「少一个候选」，是**把这次尝试的 DNS 整体变成失败**。池子从 12 降到 7，全部 IPv4，每个 hostname 节点的第一次尝试就落在能用的出口上。

改动只有一个条件，`_dns_bootstrap_for_attempt` 的轮转规则、`mihomo.py` 的 DNS 配置、扫描集合与产物契约都不动。

## Alternatives considered

### Why not 沿用「订阅数据侧抖动」这个结论，不改代码？

最强理由：上一轮生产实录已经据此结案，同一批节点在刚跑完的那次成功运行里确实正常，代码看起来没坏；把 13 条失败解释成外部抖动，是最省事也最不需要冒风险的读法。不选的原因：证据推翻了它（见 Problem 的三条）——域名有 A 记录、失败集合能被一条算术规则逐条预测、候选池的 IPv6 位置与失败索引的模完全对上。留在原地等于把一个可复现缺陷的第一次复发留到下一次，而且它已经污染过一次结论：`scan_unavailable` 的排查方向被引到了订阅内容上。

### Why not 只把 IPv4 候选排在池子前面，IPv6 留作后备？

最强理由：不丢能力——真有 IPv6 出口的主机上仍可拿 IPv6 节点引导，只把「优先用哪个」调了一下，改动比删候选更小。不选的原因：取模选中的位置由订阅顺序决定，落在 IPv6 段的那批节点仍然三次尝试全落空；失败只是从「必然」变成「看订阅顺序」，没被消除。

### Why not 保留 IPv6 候选，但用之前先探活？

最强理由：判据最贴近事实——不假设运行环境有没有 IPv6，而是当场问一次；在双栈主机上这些节点能继续当引导出口。不选的原因：要引入一次带超时的网络探测并把它放进每次尝试的选择路径，而它换来的信息我们已经有更硬的版本：四个 DoH 解析器都是 IPv4 字面量，出口必须能走本机 IPv4 栈到达。探测把「确定性」换成「每次都付的延迟」，还要处理探测本身失败的口径。

### Why not 运行时探测本机是否有 IPv6 出口，有则保留 IPv6 候选？

最强理由：在双栈主机上一点能力都不丢，判据写成「环境支持 IPv6 就允许 IPv6 引导」，最贴近直觉。不选的原因：为了一个当前跑不到的分支（生产环境的 IPv6 出口——实测见 [mihomo 允许 IPv6 笔记](2026-09-23-mihomo-allow-ipv6.md)）凭空加一套环境探测，还要把结果带进选择路径和证据字段；收益是零，维护面是常驻的。真有一天运行环境有 IPv6，改这个条件是三行的事。

### Why not 把 IPv6-only 节点（14/15/16/24..28）从扫描集合里剔掉，让失败数直接归零？

最强理由：失败数立刻从 15 降到 10 以下，扫描更快，页面上也更好看。不选的原因：那是让报告变好看，不是把问题消除。这些节点在能走 IPv6 的环境里可用，「失败行各自带原因」本来就是这张表的价值所在；把一个「跑不通但看得见」的节点删掉，等于替用户决定他不需要知道这笔订阅里有它。

### Why not 直接把 mihomo 的 `ipv6` 打开，让那 8 个 IPv6-only 节点能连？

最强理由：这是唯一看起来「改一个开关就解决」的路——`mihomo.py` 里 `ipv6` 与 `dns.ipv6` 都是 `False`，而那 8 个节点确实需要一个能被解析 / 拨通的 IPv6 地址；`v6-aws-*.aikunapp.com` 在三个公共解析器上都有 AAAA（2406:da14:… / 2406:da1e:… / 2406:da18:…），关掉 AAAA 就等于把它们从「连不上」提前成「解析不出来」。这条也是用户明确提出的方向。
不选的原因：**这条已被推翻——那一轮实验不成立。** 探针分支派出的 run `35802318111` 跑的不是分支代码：`.github/workflows/scan.yml` 的 checkout 写死 `with: ref: main`，从任何分支派发都拉 main 的 `backend/app/mihomo.py`，里面 `ipv6` 仍是 `False`；「文案一字不变」正是它没生效的证据，不是开关无效的证据。本轮用「分支探针 + 覆盖 checkout 的 `ref`」重做：两处开关都打开后，14/15/16 与 24..28 的文案**逐条**变成「节点服务器网络不可达」，整轮 30 完整 / 0 部分 / 10 失败。**该开关已正式采纳**，见 [mihomo 允许 IPv6 笔记](2026-09-23-mihomo-allow-ipv6.md)——它买到的是口径（把「本环境没有 IPv6 出口」从「订阅数据的坏」里分出来），不是成功率：那 8 个节点仍然连不上，因为 runner 没有 IPv6 默认路由。

## Consequences

- **收益（实测）**：失败数从 15 降到 10。改动后一共跑了三次生产闭环，结果依次是 30 完整 / 10 失败、30 完整 / 10 失败、27 完整 / 2 部分 / 11 失败——**本改动针对的那 5 个节点（2,3,4,38,39）三次全部成功**（改动前那次它们全部失败）。剩下那点波动来自下面那条就绪竞态与采集超时，不是解析路径的问题。
- **收益（实测）**：整轮尝试次数从 79（19 个 1 次 + 3 个 2 次 + 18 个 3 次）降到 66~67（三次分别是 66 / 66 / 67），因为「第一次尝试撞上 IPv6 候选」的那批节点不再白烧重试。
- **代价（本改动暴露出来的既有抖动，同一轮已查清并修掉）**：每轮都有若干次尝试报「Mihomo selector 切换失败（HTTP 404）」，重试有时能好；撞上的节点集合逐轮只部分重合（run2：11,12,19,20,34,36；run3：8,11,14,22,29,34,36；run4：11,18,22），不是某个候选坏了。**它就是就绪竞态**：`mihomo.start()` 原本只等 `/version`，而 mihomo 的 `hub.ApplyConfig` 先 `applyRoute`（`go start(cfg)` 起控制端口）再 `executor.ApplyConfig`（`updateProxies` 才填 `tunnel.Proxies()`），控制端口会先接客，这一小段里 `/proxies/BEST-IP` 就是 404。改动后第 7 轮（run `35803348524`）69 次尝试里撞上 16 次，终态打掉 4 个节点（14/16/22/32），其中节点 32「德国」本来是健康节点。**更正一次**：这条错因一度被我记为「实测证伪」——那次探针把「`start()` 返回后组端点是否 200」当判据，而老的 0.2 s 轮询让 `start()` 通常在 `/version` 首次成功后约 100 ms（最多 200 ms）才返回，早已越过实测 1~59 ms（中位 27 ms）的窗口，所以 16/16「没复现」是那个方法的必然结果，不是反证。修法与取证见 [selector 就绪竞态笔记](2026-09-23-selector-readiness-race.md)。
- **收益**：`scan_unavailable` 的排查方向被纠正——原来的「先查订阅内容」会把下一个查日志的人带偏，现在这条信号真有数据侧的成因时才出现。
- **代价**：候选池从 12 降到 7。在真有 IPv6 出口的主机上，那 5 个 IPv6 字面量节点不再参与引导。这是刻意的：四个 DoH 解析器都是 IPv4，一个只能走 IPv6 到达的出口本来就送不出这些查询。
- **代价**：一次尝试只换一个候选，池子小了意味着三次重试覆盖面小了（7 个候选里最多试 3 个）。真正需要的是「候选能连」，不是「候选多」，但这意味着池子里出现连不上的 IPv4 节点时，重试的兜底能力比改前弱一点。
- **仍会失败、且不是这个缺陷**：节点 22,23 的 server 是 `127.0.0.1`，是订阅方塞的广告占位节点，必然「拒绝连接」；节点 24..28 的 server 是 IPv6 字面量、节点 14/15/16 的域名（`v6-aws-*.aikunapp.com`）在三个公共解析器上**没有 A 记录、只有 AAAA**，这些都需要运行环境有真实的 IPv6 出口才能用。它们继续显示为失败并各带原因，**不**在本改动范围内消除。
- **已查清（本轮）**：节点 14/15/16 与 24..28 曾一律报「节点服务器域名无法解析」，那是 `dns.ipv6` 与顶层 `ipv6` 都关着时 mihomo 拿不到 AAAA 的后果——对 24..28 这种 server 就是 IPv6 字面量的节点更是无中生有的指控。开关打开后文案变成「节点服务器网络不可达」，如实指向「运行环境没有 IPv6 出口」。`_summarize_mihomo_error` 的分档本身没改，也不需要为这类节点单开一档；见 [mihomo 允许 IPv6 笔记](2026-09-23-mihomo-allow-ipv6.md)。

## Testing

- **失败集合的可预测性（本地重放，产物为判据）**：拿生产 run `35801218260` 的产物与同一份订阅，把候选池与 `(node_index + attempt - 1) % len(候选)` 代进去预测：18 个 hostname 节点的预测尝试次数与产物 `attempt_count` **逐条相同**，8 个「三次候选全是 IPv6」的节点预测失败且实际全部失败——本改动前的行为被完整复现。
- **改动后同一份输入的重放**：候选池 12 → 7 且全部 IPv4；节点 2,3,4,38,39 的第一次尝试从「加拿大/英国/法国 IPv6」变成「英国/卢森堡/加拿大」等 IPv4 出口，节点 5,6,17,18 的第一次尝试也不再落在 IPv6 上。
- **域名确实活着（本机 DoH，非系统解析器）**：本机系统解析器被本地 fake-ip（198.18.0.0/15）接管，所以判据走 HTTPS DoH：三个公共解析器对上述四个域名给出一致的 A 记录；`v6-aws-*.aikunapp.com` 三家都 **A 为空（Status=0）但 AAAA 有值**（2406:da14:… / 2406:da1e:… / 2406:da18:…，AWS 机房段）——它们是真的 IPv6-only，不是死域名；`neokocloud.host` 三家都是 NXDOMAIN（Status=3）。
- **门禁**：`uv run --no-dev ruff check .`（All checks passed）、`npm run check`、`npm run verify-notes`、`npx --no-install wrangler deploy --dry-run` 全绿。
