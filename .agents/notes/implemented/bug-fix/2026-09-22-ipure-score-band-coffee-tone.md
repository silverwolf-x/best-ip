# Agent Note: IPure 色带改用 Coffee 色调配方，受限项与占位一并补上对比度

Status: implemented

## Problem

前端把 ipure.dev 官网的五个页面主色**直接当分数文字色**用（`#E8447D` / `#F2734E` / `#F2C14E` / `#8DE86A` / `#34E5C4`），
药丸底色与描边只是同色 14% / 45% 的透明度。这五个色是按「大色块装饰」选的，不是按「小字可读」选的：
在浅色主题的白色卡片上，0–100 全量程的对比度是 **1.42–3.2:1**，11–12px 粗体文字的 AA 门槛（4.5:1）**一个锚点都没过**。

| 分数 | 原色 | 药丸底上对比度 |
| --- | --- | --- |
| 0 | `#E8447D` | 3.2:1 |
| 25 | `#F2734E` | 2.5:1 |
| 50 | `#F2C14E` | 1.6:1 |
| 75 | `#8DE86A` | **1.4:1** |
| 100 | `#34E5C4` | 1.5:1 |
| 全量程最低 | — | **1.42:1 @ 75 分** |

同排的 Coffee 评分走的是另一套：`--good`/`--warn`/`--danger` 深色文字 + 同色浅底 + 同色描边，
浅色 4.87 / 5.93 / 6.12:1、深色 4.87 / 6.18 / 6.28:1，全部过线。两列评分并排时，
差异不只是「一边深一边亮」——IPure 那一列的亮度还随分数起伏 1.4→3.2:1，同一屏里读起来忽明忽暗。

顺带量到：`-1`（地区受限）沿用的官网中性灰 `rgb(139 155 171)` 在浅色只有 **2.85:1**；
`.score-none`（「暂无评分」的「—」）用的 `--text-muted` 在 `--bg-soft` 上只有 **2.92:1**。两处同样低于 AA。

还有一处只在线上成立的问题：详情弹窗的 IPure 分数**从来没有上过色**。生产的 CSP 是
`style-src 'self'`（不含 `'unsafe-inline'`，见 `worker/responses.js`），而详情弹窗的分数节点是用
`innerHTML` 拼好 `style="color:…"` 再插进 DOM 的——由标记解析出来的 `style` 属性会被浏览器拦掉，
只有 CSSOM（`element.style.*`）赋值不算内联样式。本地 `scripts/dev.py` 不经 Worker、不发这个头，
所以这个缺陷**只在生产可见**，本地怎么看都是对的。表格分数格用 `style.cssText` 因而一直正常，
同一份色带在两个出口表现不一致。机制与规则见
[前端样式必须走 CSSOM](../architecture/2026-09-22-frontend-csp-blocks-markup-styles.md)。

## Decision

**分段与插值不动，只换色调。** `frontend/src/results.js` 的色相停靠点仍是 0 品红 → 25 橙红 → 50 黄 → 75 绿 → 100 青，
仍是五段、仍按位置逐通道线性插值取整。变的是每个锚点自己的颜色值。

**锚点按「固定亮度带 + 该亮度下的饱和上限」生成，两套主题各一套。**
亮度带钉在 oklch L≈0.48–0.51（浅色）与 0.69–0.72（深色）——正好是 Coffee 的 `#1d7a3a`（L=0.511）与 `#3fb950`（L=0.695）所在的那条带；
chroma 取该亮度下 sRGB 上限的 0.9 倍（浅色均值 0.128，Coffee 三个 token 均值 0.126）。
每个锚点都要求在**底色、行悬停底色、浅底块**三种承载面上、连同药丸底（同色 14%）一起 ≥4.5:1：

| 分数 | 浅色墨色 | 深色墨色 |
| --- | --- | --- |
| 0 | `#B32059` | `#F87399` |
| 25 | `#A93B17` | `#F87A55` |
| 50 | `#7A5D17` | `#C69A2D` |
| 75 | `#336E17` | `#58B52C` |
| 100 | `#1A6D5D` | `#31B399` |

结果：0–100 全量程最低对比度 **5.06:1**（浅色）/ **5.14:1**（深色），且**锚点之间不再有色阶塌陷**——
原来最暗的 0 分（3.2:1）与最亮的 75 分（1.4:1）之间差 2.3 倍，现在全落在 5.06–5.53:1。

**两套锚点只差亮度，色相与分段完全相同**，所以同一个分数在两种主题下的色相位置一致，不会出现「切主题后 60 分换了个颜色种类」。

**`-1` 保留官网中性灰的色相与饱和度，只压亮度。** `rgb(139 155 171)` 的蓝灰（`#8B9BAB` 同族）保留，
亮度解到 ≥4.5:1：浅色 `#556372`（5.06:1）、深色 `#93A3B3`（5.30:1）。受限项**仍然不带色相**，
「不在刻度上」这个语义没有被削弱——它只是从「读不清」变成「读得清」。

**`.score-none` 占位另开一个 token。** 新增 `--score-none-ink`：浅色 `#6a727c`（在 `--bg-soft` 上 4.62:1）、
深色沿用 `#8b949e`（5.62:1，本来就不缺）。**不动 `--text-muted` 本身**——它在浅色下被 `--bg-soft`、白卡片、
`--bg-hover` 上的十余处次要文字共用（统计标签、卡片标题、键值键名、表头、页脚），
整体压暗等于重排整个应用的视觉层级，远超「分数占位读不清」这件事。

**受限档与占位的取值域、哨兵语义、排序/筛选规则都没动**：`-1` 仍是 `-1`，仍不参与数值比较。

## 契约变化：内联样式只写通道，主题分发落在 CSS

`ipureScoreInlineStyle(score)` 的返回值变了：以前返回具体颜色
（`color:rgb(...);border-color:rgba(...);background:rgba(...)`），现在只返回两组通道
`--sc-l:<r g b>;--sc-d:<r g b>`。前景、描边、底色的透明度与主题选择都在 `frontend/styles.css` 里完成：

```css
.score-band, .chip-score {
  --sc: var(--sc-l, 85 99 114);
  color: rgb(var(--sc));
  background: rgb(var(--sc) / 0.14);
  border: 1px solid rgb(var(--sc) / 0.45);
}
@media (prefers-color-scheme: dark) { … :is(.score-band, .chip-score) { --sc: var(--sc-d, 147 163 179); } }
:root[data-theme="dark"] :is(.score-band, .chip-score) { --sc: var(--sc-d, 147 163 179); }
```

**为什么主题分发必须在 CSS：** `ui.js` 的主题切换只改 `documentElement.dataset.theme` 并写 localStorage，
**不重渲染节点**。内联样式在渲染那一刻写死，切主题后颜色会停在旧主题上。用 CSS 自定义属性则切换即时生效。
`--sc` 与它引用的 `--sc-l`/`--sc-d` 都声明在**同一个元素**上（通道来自内联、选择来自样式表），
不跨元素继承，因此不依赖「自定义属性惰性代入」这类边界行为。

**着色点仍然唯一：** 表格分数格、场景 chip、详情 hero 总分框都只拿到这两组通道，
任何一处都不可能单独选色。旧的 `.score-band { border: 1px solid transparent }` 与
「`.chip-score` 靠内联 `border-color` 但从未声明 border-width（等于没有描边）」这对不一致一并去掉——
两者现在共享同一条规则。

**调用面：`ipureScoreInlineStyle(score)` 的签名与「返回空串表示没有分数」的约定不变，
两个视图文件的导入与判空逻辑也都不用改。** `ipureScoreChannels` / `ipureScoreColor` /
`IPURE_RESTRICTED_CHANNELS` 增加了 `theme` 参数，但三者在仓库内**没有 results.js 之外的调用方**。
`table-view.js` 因此一行没改（它本来就用 `badge.style.cssText`）；`detail-view.js` 只改了通道的传递方式，
没有改判空、也没有改任何渲染分支。

**详情弹窗的分数通道改走 CSSOM。** 分数节点不再拼 `style` 属性，而是带上 `data-ipure-score`，
在 `elements.detailContent.replaceChildren(...)` **之后**由 `applyIpureScoreStyles()` 统一写入
`element.style.cssText = ipureScoreInlineStyle(score)`。这既绕开 CSP（原因见 `## Problem`），
也让「通道从哪来」在详情视图里只剩一个落点。今后任何新增的「带分数的标记」都必须走这条路径，
不能把通道拼回 `innerHTML`——那样本地看着正常、线上是灰的。

## Alternatives considered

**只改浅色主题，深色主题保留官网原色。** 最强理由：深色下官网原色是 3.97–8.3:1，已经达标，
用户抱怨的本来就是浅色；只动一处，改动面最小，深色观感零风险，也无须引入两套锚点。
否定理由：深色下 0 分品红 3.97:1 与 75 分绿 8.3:1 差了 2.1 倍——「同一列分数忽明忽暗」正是要修的那件事，
只修浅色等于把它留在另一半用户那边。这条作为保守选项在确认时提供给了用户，用户选择两套都改。

**压暗官网原色、保留其色相与饱和度，不做统一亮度带。** 最强理由：与官网报告页色相一一对应，
改动最小，也不需要解释「亮度带」「chroma 上限」这套生成规则。
否定理由：黄色锚点在白底上**没有既亮又饱和的可行解**——要过 4.5:1 就必须压到 L≈0.5，
压到那里黄色自然变成橄榄金、绿色变成深绿，结果与统一亮度带几乎一模一样；
差别只在于每个色各压多少变成手调的，没有可复算的判据，下一步改主题时又要重新拍。
保留色相、按固定亮度带解值，把「压多少」变成由对比度目标反解出来的量。

**改成与 Coffee 一样的三档分桶（`score-great` / `score-good` / `score-bad`）。** 最强理由：
完全复用现成 class 与 token，不用新增通道变量，两列评分在结构上真正统一，代码还更少。
否定理由：这正是[旧笔记已否决过的方案](../architecture/2026-09-21-ipure-restricted-sentinel-and-score-band.md)，
理由没有变——三档会在同一档内产生色阶跳变，与用户自己打开的 ipure.dev 报告页对不上。
本次**只借用 Coffee 的色调配方，没有借用它的分桶**：仍是五段连续插值，色相顺序与官网相同。

**让 `ipureScoreInlineStyle` 在渲染时读当前主题，直接返回具体颜色。** 最强理由：不需要 CSS 自定义属性这一层间接，
函数读起来直白，`results.js` 仍然是唯一知道颜色是什么的地方。
否定理由：主题切换不重渲染（见上），内联颜色会停在切换前的主题；
要补就得在切主题时整表重渲染，为一个配色去动渲染时序、把「配色」和「重渲染」耦合成一条隐式依赖，不值得。

**`-1` 继续沿用官网的 `--color-ink-dim` 原值。** 最强理由：与官网逐字一致，
而且受限项本来就不是分数，中性灰的语义是对的。
否定理由：那个灰在浅色只有 2.85:1，会和色带一起读不清——「不在刻度上」和「看不清」是两件事，
前者靠「无彩色相」表达就够了，不需要连可读性一起牺牲。保留色相与饱和度、只解亮度，两者都拿到。

**给 Worker 的 CSP 补上 `style-src 'unsafe-inline'`，让原来的 `innerHTML` 写法直接生效。** 最强理由：
一个头的改动，前端一行都不用动，也不必引入 `data-ipure-score` 这层数据属性，
详情弹窗立刻就能上色；而且「内联样式」本来是这版前端一直在用的写法，放行它等于让线上的行为与本地一致。
否定理由：这会让 `style-src` 这道防线整体失效——`style-src` 正是用来兜住「标记里混进任意 CSS」的，
放行之后任何将来注入到标记里的样式都会生效，而本仓库的部署后自证又把 CSP 当作要检查的线上约束之一；
更关键的是它**没有解决分歧本身**：本地不发 CSP、线上发，任何一次「拼 style 属性」仍然会在本地看着正常、
线上静默失效。把写法改成 CSP 下本来就合法的 CSSOM，才是消掉这条 dev/prod 分叉的做法。

## Consequences

- 收益：0–100 全量程最低对比度 从 1.42:1 提到 **5.06:1**（浅色）/ 5.14:1（深色），全部过 AA；
  同一列不再有 2 倍以上的亮度起伏。
- 收益：IPure 分数列与 Coffee 评分列现在是同一套色调语言（墨色文字 + 同色浅底 + 同色描边），
  并排读不再需要两套解读习惯。
- 收益：受限项 `-1`（2.85→5.06:1）与 `.score-none` 占位（2.92→4.62:1）一并过线。
- 收益：颜色只有一个产生点（`results.js` 的通道），只有一处消费配方（`styles.css`），
  且 `--sc` 带兜底通道，漏带内联样式的元素不会退化成无效颜色。
- 收益：详情弹窗的 IPure 分数在**生产上第一次真正带上色**——此前它的 `innerHTML` 样式一直被 CSP 拦掉，
  表格（`style.cssText`）、chip、hero 三个出口第一次一致。
- 代价：`ipureScoreChannels` / `ipureScoreColor` / `IPURE_RESTRICTED_CHANNELS` 的签名与形状变了
  （多了 `theme`，受限通道从数组变成 `{light, dark}`）。仓库内只有 `results.js` 自用，
  但这是对已导出符号的破坏性收窄，外部脚本按老签名调用会拿到浅色通道而不报错。
- 代价：50 分的黄在浅色主题里只能是橄榄金（`#7A5D17`）。这是色彩空间的硬约束——
  黄色要在白底上到 4.5:1 就必须压到 L≈0.5，没有更亮又达标的解。Coffee 自己的琥珀 token 就是 `#7a5a00` 同款处理。
- 代价：浅色主题的分数列整体变「深」了，比改动前少了一份鲜艳。这是用鲜艳换成可读，
  若日后要换回来，代价是重新掉到 AA 线下。
- 代价：`--score-none-ink` 是为了不牵动 `--text-muted` 而新增的第四个文字层级 token，
  语义上与 `--text-muted` 高度重叠。重访信号：如果哪天决定整体修 `--text-muted` 的浅色值，
  这个 token 应当与 `.score-none` 的引用一起删掉。
- 未处理（相邻发现，未纳入本次改动）：`--text-muted` 在浅色下被十余处次要文字共用，
  在白卡片上只有 3.07:1、在 `--bg-soft` 上 2.92:1，**普遍低于 AA**。压暗它会重排整个应用的视觉层级，
  与「分数色带可读」是不同的决定，因此留给独立的一次改动。

## Testing

对比度不是目测，是算出来的：三段亮度带、chroma 上限、`-1` 中性色与 `--score-none-ink` 的值都由一个 scratch 脚本反解，
它在 oklch 空间扫描 L、逐点验证「底色 + 药丸底 + 行悬停底色」三项达标后取极值；
0–100 每 5 分逐格打印对比度，改动前 1.42:1、改动后 5.06:1 都是这个脚本的输出。

浏览器里实测确认过（临时预览页 `frontend/preview-palette.html`，确认后已删除，未提交）：

- 页面直接 import 真实的 `results.js` / `table-view.js` / `styles.css`，12 行样例走真实的 `createResultRow`，
  不是另画一套 DOM。
- `style.cssText` 写入自定义属性确实生效：`--sc-l: 179 32 89` → 计算样式 `rgb(179, 32, 89)`。
- 深浅两套通道随主题切换正确：受限项 `-1` 在浅色为 `rgb(85, 99, 114)`、深色为 `rgb(147, 163, 179)`；
  96 分在深色为 `rgb(55, 179, 136)`，与同排 Coffee 92 分的 `rgb(63, 185, 80)` 同一亮度带。
- `.score-none` 的「—」浅色计算样式 `rgb(106, 114, 124)`（4.62:1）、深色 `rgb(139, 148, 158)`（5.62:1）。
- 0–100 每 5 分共 21 格，**相邻格颜色无重复**，色带没有塌陷；页面无横向溢出。
- `npm test`（`node --check` 全量语法检查）通过。

`ipureScoreChannels` 的空值语义未变：`null`/空串、`-2`、`101` 仍返回 `null`（无色），
`-1` 返回中性通道，`0..100` 返回插值结果。
