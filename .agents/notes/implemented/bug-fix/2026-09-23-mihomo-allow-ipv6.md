# Agent Note: mihomo 允许 IPv6 —— 把「本环境没有 IPv6 出口」从「域名无法解析」里分出来

Status: implemented

## Problem

生产闭环每轮稳定留下 8 条失败，文案都是「节点服务器域名无法解析」：

- 节点 14/15/16（`2x专线-{日本,香港,新加坡}-4 (IPv6)`），server 是 `v6-aws-{jp,hk,sg}.aikunapp.com`——三家公共 DoH 都是 **A 为空、AAAA 有值**（2406:da14 / da1e / da18，AWS 段）。
- 节点 24..28（`加拿大/英国/法国/德国/卢森堡 IPv6`），server 直接就是 IPv6 字面量（`2607:5300:205:200::7996` 等）。

这两类节点的地址是活的，**是扫描器自己不去取**：`mihomo.py` 顶层 `"ipv6": False`（mihomo 的语义是「开启 IPv6 总开关，关闭阻断所有 IPv6 链接**和屏蔽 DNS 请求 AAAA 记录**」），`_DEFAULT_DNS_CONFIG["ipv6"] = False`（「false 将返回 AAAA 的空结果」）。两处都关着时，mihomo 对这两类节点连地址都拿不到，日志里的 `dns resolve failed` 被 `_summarize_mihomo_error` 读成「节点服务器域名无法解析」——**一个地址族开关冒充成了订阅数据的坏**，排查方向被引到订阅内容上（见 [DNS 引导笔记](2026-09-23-dns-bootstrap-ipv6-poisoning.md) 里那次被它带偏的更正）。

运行环境的真实情况本轮实测（方案见 Testing）：

- `ip -6 addr`：只有 `lo ::1/128` 与 `eth0 fe80::7eed:8dff:fe86:e065/64`；
- `ip -6 route`：只有 `fe80::/64 dev eth0`，**没有默认路由**；
- `curl -6` 立刻失败（`Couldn't connect to server`, rc=7），`socket.connect(("2606:4700:4700::1111", 443))` 报 `OSError [Errno 101] Network is unreachable`。

GitHub 官方在 `actions/runner-images` 上多次说明托管 runner 不支持 IPv6 进出网且没有 ETA（issue #9401 / #9540 / #668），与实测同向。**所以「本机没有 IPv6 出口」是环境事实，不是配置问题。**

## Decision

`backend/app/mihomo.py` 两处都开：`_DEFAULT_DNS_CONFIG["ipv6"] = True`（dns.ipv6）与顶层 `"ipv6": True`。出站允许 IPv6，DNS 返回 AAAA。

这条改动买到的是**口径，不是成功率**。那 8 个节点在本环境依旧连不上（没有 IPv6 默认路由可走），但失败文案从「节点服务器域名无法解析」变成「节点服务器网络不可达」（`network is unreachable` 的既有映射）——后者指得准：问题是扫描环境缺一条 IPv6 出口，不是订阅里的节点坏了。AAAA 也确实回到了解析链路上，否则连这句话都说不出来。

不能反过来「先只改文案」：要区分「域名真没有 A 记录」和「我们没问 AAAA」，必须先拿到 AAAA 的结果，也就是先开开关。顺序不可颠倒，这是本决策的直接理由。

开关是全局的，只在 `mihomo.py` 两处；`_dns_bootstrap_candidates` 只收全局 IPv4 字面量的判据**不变**（引导出口要把 DoH 查询送到四个 IPv4 解析器，与本开关无关）。

## 上一轮的「零收益」结论是被一次无效实验带出来的

[DNS 引导笔记](2026-09-23-dns-bootstrap-ipv6-poisoning.md) 里写着「在生产上实测过：打开这个开关不解决问题，零收益，不采纳」，依据是探针分支 `probe/ipv6`（commit `bf8631d`）派出的 run `35802318111`。**那次实验不成立**：

`.github/workflows/scan.yml` 的 checkout 步骤写死 `with: ref: main`——**从任何分支派发都拉 main 的代码**。那个 run 的 `headSha` 确实是 `bf8631d`，但 runner 上执行的是 main 的 `backend/app/mihomo.py`，里面 `ipv6` 仍是 `False`。变了的是分支上的文件，不是被执行的文件；「文案一字不变」正是它没生效的证据，而不是「开关无效」的证据。

派分支探针的正确姿势：把 checkout 的 `ref` 指到派发的 ref（`ref: ${{ github.ref_name }}`），或者干脆把改动落到 main 再派。**判据：`headSha` 与被执行代码不一致时，结果不能用来下结论。**

## Alternatives considered

### Why not 保持 ipv6 关着，只把报错文案改准？

最强理由：问题出在文案，最省事的就是不动地址族策略，只在 `_summarize_mihomo_error` 里给这类节点单独分档，风险面只有翻译表。不选的原因：关着的时候 mihomo 根本不返回 AAAA，日志里没有能区分「域名确实没有 A 记录」和「我们主动没问 AAAA」的信息——想改文案就得先有 AAAA 的结果，也就是先开开关。顺序反过来做不到，所以文案问题是从属于本决策的。

### Why not 把 IPv6-only 节点（14/15/16、24..28）从扫描集合里剔掉，让失败数直接归零？

最强理由：失败数立刻从 10 降到 2，扫描更快，页面上也更好看。不选的原因：那是让报告变好看，不是把问题消除——这 8 个节点在用户自己的客户端（有 IPv6）里可用，删掉等于替用户决定他不需要知道这笔订阅里有它；DNS 笔记里同一条已被否过。**这一条继续不采纳，需要时另开决定。**

### Why not 给扫描环境一条真实 IPv6 出口（自托管 runner 或隧道）？

最强理由：这是唯一能让那 8 个节点**真的成功**的路——不是改判据，是补能力；自托管 runner 上这些节点与本地行为一致。不选的原因（本轮）：这不是代码改动，是运行环境与成本决定（自托管 runner 或第三方隧道 + 运维 + 出口 IP 归属变化），必须由使用方拍板；本轮把它记成明确的下一步，而不是顺手做。

### Why not 用 IPv4 节点做 `dialer-proxy` 中转，把「拨号」交给有 IPv6 的节点？

最强理由：不需要本机 IPv6 就能救回那 8 个节点——mihomo 支持让某个节点经另一个代理建立连接，中转节点自己有 IPv6 即可。**本轮实测可行**（见 Testing）：`2x专线-日本-4 (IPv6) ← 英国` 目标节点延迟 2405 ms、出口 `13.113.137.15`（AWS 东京，正是该节点自己的出口）；`2x专线-香港-4 (IPv6) ← 卢森堡` 1348 ms、出口 `18.167.52.27`（AWS 香港）；不加中转的对照组是同一次运行里的 503 + `write udp [::]:... error`（无 IPv6 路由的典型现场）。出口 IP 是目标节点自己的，所以「出口归属地/评分」这类节点侧指标不受中转影响。

不选的原因：它改的是**测量语义**，超出「允许 IPv6」这个开关的范围——节点变成经中转到达，路径相关指标（`global_ping`、`elapsed_ms`、咖啡页耗时）里含中转那一跳，与用户直连不等价；而且要给扫描器加一层「挑谁当中转、怎么确认它有 IPv6」的策略与证据字段。这属于产品决定，本轮只落数据、不落实现。

### Why not 顺手给节点加 `ip-version: ipv4` 把测量地址族钉死？

最强理由：`ip.net.coffee` / `ipure.dev` 是 Cloudflare 双栈，开着 AAAA 后双栈节点可能改走 IPv6 出口，会让同一个节点的「出口 IP」在两次快照间换地址族，破坏可比性。不选的原因（本轮）：本轮 30 个成功记录的出口 IP **全是 v4**（与关着时一致，首行三项也与历史逐字相同），没有出现实际换族；先把这条记成观察项——真在产物里看到 v6 出口再钉，比现在预先钉死更省事，也不提前砍掉 IPv6 节点的能力。

## Consequences

- **收益（实测）**：那 8 条「节点服务器域名无法解析」不再出现——失败文案改成「节点服务器网络不可达」，诊断指向从订阅数据挪回扫描环境。这是本轮改动唯一的实际产出。
- **收益**：开关本身就是「将来给扫描环境接上 IPv6 出口」的前置条件。出口一旦有了，本改动无需再动。
- **风险（已观察，未触发）**：开启 AAAA 后，双栈节点理论上可以让 `ip.net.coffee` 的探测经由 IPv6 出去，使 `exit_ip` 变成 v6 地址，破坏与历史快照的可比性。本轮有效探针的 30 个成功记录里 v6 出口为 **0**，首行 `exit_ip=104.238.221.29 / coffee=67 / score=39` 与改动前逐字相同，所以本轮没有实际换族；继续按轮次看产物里的 `exit_ip` 地址族即可发现。
- **代价**：mihomo 的地址族策略从「全程 v4」变成「双栈」，这是一个全局开关，影响所有节点与所有目标域名的解析；本轮用一次生产形状的完整扫描（30 条成功记录全部落表、产物通过页面自己的 `reader.js` 校验）作为没有退化的证据，但它不是「所有双栈组合都测过」。
- **仍未解决（本改动范围外）**：8 个 IPv6-only 节点在本环境继续失败（已量出中转可行，见上文备选方案）；节点 22/23 的 server 是 `127.0.0.1`，是订阅方塞的广告占位节点，必然「拒绝连接」。原先还挂着「每轮若干次尝试撞上 selector 404」——它已在 [selector 就绪竞态笔记](2026-09-23-selector-readiness-race.md) 里查清并修掉（就绪只等 `/version`、不等组注册；run `35803348524` 里 69 次尝试撞 16 次、终态打掉 4 个节点，含健康节点 32）。
- **代价**：`ipv6: true` 让 mihomo 需要处理 AAAA 结果，日志噪声与解析路径都比纯 v4 复杂；本环境拿不到 IPv6 出口时，这份复杂度换来的只有文案正确。

## Testing

- **runner 有没有 IPv6 出口（在 runner 上实测，非推断）**：在扫描工作流里临时加一步诊断（`ip -6 addr` / `ip -6 route` / `/proc/net/if_inet6` / `curl -6` / `socket(AF_INET6)` 连接），run `35802818387` 的输出即 Problem 里那四条。同向的官方说明见 actions/runner-images #9401 / #9540 / #668。
- **有效探针（这一次分支代码真的被执行）**：同一条 run `35802818387` 上，把 checkout 的 `ref` 指到派发分支并让 `mihomo.py` 两处为 `True`，得到 **30 完整 / 0 部分 / 10 失败**（产物 123393 B，`headSha=59e2e29`）。8 个 IPv6 节点的文案逐条变成「节点服务器网络不可达」；产物交给页面自己的 `frontend-next/app/artifact/reader.js` 逐字节校验通过，前 40 条记录里 30 条有出口 IP，**出口地址族 v4 30 / v6 0**，首行 `104.238.221.29 / coffee 67 / score 39` 与 main 的历史运行逐字相同。
- **中转可行性（同一分支，`scripts/probe_ipv6_relay.py`，run `35803149224`，commit `0cbb3d4`）**：给目标节点写 `dialer-proxy: <IPv4 节点>`，用 mihomo 自己的 `/proxies/{name}/delay` 量目标节点：日本-4←英国 2405 ms、香港-4←卢森堡 1348 ms、加拿大 IPv6←加拿大 204 ms、英国 IPv6←英国 479 ms，出口 IP 分别是 `13.113.137.15` / `18.167.52.27` 等目标节点自己的地址；对照组（加拿大 IPv6 不加中转）HTTP 503，日志 `dialer PROBE ... error: write udp [::]:...`。脚本与工作流改动都只存在于探针分支。
- **门禁**：`uv run --no-dev ruff check .`、`npm run check`、`npm run verify-notes`、`npx --no-install wrangler deploy --dry-run` 全绿。
