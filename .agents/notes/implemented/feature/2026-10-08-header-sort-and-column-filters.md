# Agent Note: 表头点击排序与逐列筛选

Status: implemented

## Problem

排序只能靠顶部的「排序」下拉，而且只有 Coffee、IPure、节点名三种键；按出口 IP、国家和地区、服务商、接入、原生性都排不了。筛选只有全局搜索与状态下拉，想要「只看住宅 + Coffee ≥ 70」这类组合没有入口——这正是 [单视图改版](2026-09-22-frontend-single-view-redesign.md) 在 Consequences 里记下的代价。项目的设置卡片提出「点列名排序、每列加筛选格，替换只有按钮的控件」，项目所有者点了开始。

## Decision

- 列名即排序按钮：`app/render.js` 的 `COLUMNS` 给八列加了 `sort` 键，`createHeadRow` 把列名渲染成 `.th-sort` 按钮。再点一次换方向；文本列首次点按 A→Z，分数与枚举列首次点按「好的在前」。方向只写在 `th` 的 `aria-sort` 上，CSS 据此画箭头。没值的节点在两个方向上都沉底。出口 IP 的 IPv4 按四段数值排。
- 每列一格筛选：`COLUMNS` 的 `filter` 声明控件类型——`text`（节点/协议、IP、国家/城市、服务商/ASN，包含匹配）、`select`（接入、原生性：是/否/未知）、`min`（Coffee、IPure：不低于）。判据集中在 `app/main.js` 的 `COLUMN_FILTERS`，与全局搜索、状态下拉取交集。
- 顶部的 `#sortSelect` 删除；搜索框与状态下拉保留（状态不是一列）。
- 窄屏（≤900px）表头不再是 1px 裁切盒，而是卡片上方一条两列的「列名 + 筛选格」工具条；`#` 与场景评分两列没有控件，仍只留在无障碍树里。
- 导出快照前把表头里的按钮换回纯列名、摘掉筛选格（`staticGridHtml`），离线文件里不留点不动的控件；摘要里的「筛选」写成全局搜索加各列筛选，「排序」写成列名加方向。

这推翻了单视图改版里「`thead` 内不得有任何控件」那条约定。`scripts/check_frontend_contracts.mjs` 的契约 b 只检查 `index.html` 里的静态 `<thead>`，表头由 JS 生成，它仍然通过。

## Alternatives considered

### Why not 保留排序下拉，只加表头筛选？

下拉里每加一个排序键就要加两个 option，八列就是十六项；点列名是表格的通用习惯，也让排序状态就在对应列上可见。

### Why not 把筛选做成表头弹出层？

弹出层要多一层开关状态、焦点管理和窄屏定位，而每列一格的输入框不需要任何额外状态，也一眼看得出哪列正在筛。

## Consequences

- **收益**：八列可排序，组合筛选有了入口；状态全部在内存里，渲染指纹（`renderKey`）把筛选也算进去，没变就不重建表格。
- **代价**：表头多了一行控件高度；窄屏卡片上方多了四行工具条。

## Testing

- `npm run check` 通过（语法、前端契约、mhtml 往返）。
- 真实 Chromium（示例数据）：1440 视口表格 1390px、无横向滚动；点 Coffee 列名在降序/升序间切换且无分数的两行始终在末尾；点出口 IP 按数值升序；Coffee ≥ 60 加「住宅」得到 5 行；国家筛「日本」得到 2 行；390 视口无横向滚动；导出的 .html 表头只剩列名，摘要写出「排序：出口 IP A→Z」。
